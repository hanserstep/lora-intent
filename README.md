# 工单分类 LoRA 微调

在消费级设备（M4 / 16G）上微调 Qwen2.5-0.5B，把运维工单自动分到六类。

做这个项目的理由很直接：AI 应用岗 JD 里「微调 / LoRA」出现频次 5/15，
虽然多数写的是「了解即可」，但**本科 + 无论文**在这个方向天然吃亏。
一个真实跑过的微调实验，比写十遍「了解 LoRA 原理」有说服力。

规模刻意做小：0.5B 模型、324 条数据、4 个 epoch、单机 15 分钟内跑完。
目标不是刷 SOTA，是**把「微调有没有用」这件事量化出来**。

## 任务与数据

六类工单：`disk` / `network` / `cpu` / `memory` / `database` / `other`，
和 `ops-agent` 的工具集对应，场景自洽。

数据用模板生成（`data/build_dataset.py`），324 条，每类 54 条。
每个类别 9 个模板，每个模板生成 6 个变体，变量（主机名、百分比、延迟）随机填充。

### 一个关键的划分细节

**训练集和测试集按模板划分，不随机切。**

同一模板生成的不同变体如果分别进了训练和测试，测试集测的其实是
「模型有没有背下这个模板」，准确率会虚高到 95% 以上，但没有意义。

现在的划分是 36 个模板进训练、18 个模板进测试，测试集全是模型没见过的表达方式。
这个数字才反映泛化能力，也解释了为什么准确率不会是 99%——真实场景本来就不会。

## 方法

| 项 | 取值 |
|---|---|
| 底座 | Qwen2.5-0.5B-Instruct |
| 精度 | float32（MPS 上 fp16 数值不稳，0.5B 用 fp32 只占 2G 统一内存） |
| LoRA | r=8, alpha=16, dropout=0.05 |
| 目标模块 | q_proj / k_proj / v_proj / o_proj |
| 训练 | 4 epoch，lr 2e-4，batch 2 × 累积 4，cosine 调度带 10% warmup |
| 可训练参数 | 约 1.5M（全量的 0.3%） |

两个实现细节值得说：

**loss 只算答案部分。** prompt 部分用 `-100` 屏蔽。不屏蔽的话模型会把算力
花在复述 prompt 上，loss 曲线看着漂亮但分类能力很差。

**解析器必须严格。** 只认第一个词且必须是六个标签之一。
如果用 `label in raw` 判断，「不是 disk」这种输出会被误判成 disk——
那样评测衡量的就不是模型能力，而是解析器的宽容度。

### 怎么看这组数字

**基线 0.39 不是 prompt 没写好，是 0.5B 模型的能力边界。**
六分类的随机猜是 0.167，基线只高出 2 倍多，说明它在用「关键词碰运气」而不是理解语义。
这也正是微调的动机：小模型在垂直任务上，靠 prompt 掏不出更多。

**提升主要来自「敢下判断」，不是「更懂领域」。**
看混淆矩阵，微调后 disk / network / cpu 三类全对，但 memory 有 3 条被判成 disk。
错的是「JVM 元空间溢出」——模型把「空间」关联到了磁盘。这类错在语义上说得通，
说明它学到的仍偏向字面模式。这不奇怪：训练数据只有 140 条、模板化的表达。

**训练 loss 降到 0.0008，是过拟合的信号。**
140 条数据训 4 轮，模型几乎把训练集背下来了。之所以测试集还有 0.84，
是因为划分按模板做了隔离——如果随机切分，这条曲线会漂亮得多，但那个数字是假的。

## 复现

```bash
pip install -r requirements.txt

python data/build_dataset.py          # 生成数据（几秒）
python -m src.evaluate --mode baseline # zero-shot 基线
python -m src.train --tag run1         # LoRA 训练（M4 上约 10 分钟）
python -m src.evaluate --mode lora --tag run1
```

## 项目结构

```
data/build_dataset.py   模板生成 + 按模板分组划分
src/common.py           配置、prompt、严格解析器、混淆矩阵
src/train.py            手写训练循环（loss mask / 梯度累积 / cosine 调度）
src/evaluate.py         baseline 与 lora 共用同一套评测
outputs/                adapter 与评测结果（.gitignore 排除）
```

## 已知限制

- 模板数据有固定语言模式，模型可能学到关键词匹配而非语义理解。
  要验证语义能力需要人工标注的真实工单，本项目没有。
- 0.5B 模型的知识容量有限，对没见过的领域术语（如特定中间件名）容易错。
- 只测了分类任务。指令遵循、生成质量这类能力不是这个规模能调出来的。
